01 Overview

What this machine is

The platform is a Traxxas Slash 4×4 — a four-wheel-drive RC car with Ackermann steering (the front wheels turn; there is no in-place rotation) and a single brushless drive motor. In a stock RC car a hobby receiver reads the transmitter and drives two things: the electronic speed controller and the steering servo. Here, the Jetson replaces the receiver — it decides how fast to go and how far to turn, and issues those two commands electronically.

Because one small computer now owns both jobs, the build splits cleanly into three worlds: sensing (camera, LiDAR, GPS, compass), compute (the Jetson running perception and planning), and actuation (throttle via the VESC, steering via an Arduino Nano). Everything in this document falls into one of those three.

Sensing

USB camera, RPLIDAR C1, SE100 GPS + IST8310 compass. The car's eyes and situational awareness.

Compute

Jetson Orin Nano Super — CUDA GPU running depth perception, YOLO, and (in ROS 2) SLAM + nav2 planning.

Actuation

VESC drives the motor; an Arduino Nano generates the steering-servo pulse. Two commands: throttle and steer.

03 System architecture

How data flows through the car

Sensors stream into the Jetson; the Jetson turns that into two numbers — a steering value and a throttle value — and pushes them back out to the two actuators. Everything else is detail on top of this loop.

GPS + compassttyTHS1 · i2c-7
→
Jetson Orin Nanoperception · planning
→
VESCttyACM0 → motor
Arduino NanottyUSB1 → servo D9

Two software stacks ride on this same hardware: a lean reactive path (camera → depth → steer/throttle, in autonav.py) and a full ROS 2 + nav2 path (LiDAR SLAM → map → plan → drive). They never run at once, because both want to own the VESC and the steering port.

04 Power architecture

What powers what

The single most important power rule on this car: the motor, the servo, and the Jetson each get their own supply. Sharing them causes brownouts and resets — the motor's current spikes would sag the rail and reboot the computer mid-drive.

The VESC's logic is fed from this battery, not from USB — so /dev/ttyACM0 only appears when the motor battery is on.

The Nano pin provides only the signal. Servo power must come from the BEC — never the Jetson 5 V.

Common ground is mandatory Every board — VESC, Nano, servo BEC, Jetson — must share a ground reference, or the serial links and the servo pulse become unreliable.

Jetson power (mobile plan — not yet built)

Today the Jetson runs on its wall supply (tethered). The untethered plan: a separate 3S LiPo → buck-boost regulator set to 15 V, ≥ 6 A / ≥ 100 W → barrel jack 5.5 × 2.5 mm, centre-positive (the Jetson accepts 9–19 V, drawing ~25 W peak at MAXN_SUPER). Add a 10 A inline fuse and a LiPo low-voltage alarm — RC LiPos have no BMS. Estimated runtime on a 3S 5000 mAh pack: ~1.5–2 h.

05 The 40-pin header

What's wired to the Jetson's GPIO

Only two subsystems touch the 40-pin header at all: the GPS (over the header UART) and the compass + OLED (over I2C). Everything else — motor, steering, camera, LiDAR — is USB. And critically: the steering servo is not on a Jetson GPIO pin. The Jetson can't cleanly generate a stable 50 Hz servo pulse, so that job is handed off to the Arduino Nano (pin D9 on the Nano, over USB). The header is used purely for the SE100 module.

One I2C pin pair, two devices The header exposes exactly one I2C pair (pins 3 & 5 → bus /dev/i2c-7). I2C is a shared bus, so the compass (0x0e) and the OLED (0x3c) are spliced onto the same two lines, each keeping its own VCC and GND. The UART on pins 8/10 enumerates as /dev/ttyTHS1.

06 USB & serial map

Every serial device, and why we resolve by identity

Four things talk to the Jetson over USB serial: the VESC, the steering Nano, and the LiDAR (plus the two cameras as video devices). The trap is that Linux names them ttyACM0, ttyUSB0, ttyUSB1 in plug-in order — so the numbers shift whenever a device is added or replugged.

The port-shift trap Adding the RPLIDAR pushed the steering Nano from ttyUSB0 to ttyUSB1. Any script that grabbed “the first ttyUSB” would then be sending steering commands to the LiDAR. The fix: never address by number — resolve every device by its stable /dev/serial/by-id/ identity, which never moves.

08 Drive

VESC + brushless motor

The Flipsky Mini FSESC 6.7 Pro (a VESC, hardware 6.x, firmware 5.2) drives the Traxxas Velineon 3500 brushless motor with field-oriented control. It connects to the Jetson by USB and speaks the native VESC binary packet protocol.

How the Jetson talks to it

Each command is a framed packet: a start byte (0x02 for short payloads), a length, the payload (a command id + arguments), a CRC16-CCITT checksum, and a stop byte (0x03). Key commands used:

CommandIDPurpose
GET_VALUES4Live telemetry (below).
SET_DUTY5Throttle as duty cycle. Clamped to ±0.95; packed as duty×100000.
SET_CURRENT6Torque control; 0.0 A = stop.
SET_RPM8Closed-loop electrical RPM.
SET_SERVO_POS12(Unused — VESC servo output is unreliable; see note.)

Telemetry back from GET_VALUES includes MOSFET & motor temperature, motor and input current, duty, eRPM, input voltage, amp-hours, tachometer (used for odometry), and a fault code.

Motor detection & calibration

  • Detected in VESC Tool 7.00 on a 3S LiPo: 4 poles, sensorless; R = 10.4 mΩ, L = 0.68 µH, flux linkage = 0.75 mWb. Direction came out reversed and was inverted in the tool.
  • Bench-verified: a 5 % duty ramp spun all wheels smoothly — ~2800 eRPM, ~4.6 A, 11.7 V, fault 0. Forward and reverse confirmed.
  • Odometry calibration: meters_per_tach = 0.003424 (pushed 6.8 m → Δtach 1986, ≈ 292 counts/m).
Two things to remember The VESC only enumerates when its motor battery is on (logic is battery-fed). And it self-stops if it gets no command for ~1 s — so the controller must send continuously; dropping the link makes the car coast to a stop (a safety feature, not a bug).
Why steering isn't on the VESC The VESC has a servo output pin, but driving it needs custom-compiled firmware and is buggy (erratic pulses, FOC glitches) — even Flipsky recommends an external microcontroller. Hence the Arduino Nano.

09 Steering

Arduino Nano + servo

An Arduino Nano clone (CH340 USB-serial chip, hence ttyUSB1) sits between the Jetson and the steering servo. The Jetson sends an angle over USB; the Nano turns it into the precise 50 Hz PWM pulse the servo needs, on pin D9.

Serial protocol (115200 baud, one command per line)

CommandAction
"90"Set angle to 90° (clamped to the safe range).
cCenter (90°).
dDetach — stop pulsing so the servo relaxes (no idle buzz/heat).
sSweep the full safe range and back (proves it physically moves).
?Print status. The Nano echoes ANGLE 90 / READY … so the host can confirm.

The safe steering range (asymmetric, bench-tested)

The wheels hit a mechanical stop well before the servo's electrical limits. Driving into that stop stalls the servo — it buzzes, pulls > 1 A, heats up, and can strip its gears. So every command is clamped to a bench-proven range, and the linkage swings further left than right:

60°full left · norm −1
—
90°center · norm 0
—
115°full right · norm +1

This clamp is enforced in three places so a runaway value can never reach the linkage: the firmware (STEER_MIN 60 / STEER_MAX 115), the Python driver, and any UI. The software works in a normalized −1 … +1 which maps asymmetrically onto 60–115°.

Servo power & the CH340 fixes The servo draws > 1 A under load — it must run from a separate 5–6 V BEC with a common ground, never the Jetson (it would brown out). Two host-side fixes were needed: the Jetson kernel lacked the ch341 driver (built from source), and brltty had to be removed because it hijacks CH340 ports.

10 Camera

USB vision

Two identical icSpring USB webcams enumerate as /dev/video0–3 (each camera presents a capture node plus a metadata node). They advertise only uncompressed YUYV at 640×480 — no MJPG — which caps the practical frame rate around 18–22 fps.

  • Exposure is pinned manually. Auto-exposure was lengthening the exposure in low light and dragging FPS from 15 down to 9 (the SoC stayed cool — it wasn't throttling). Fix: auto_exposure=1 (manual) + exposure_time_absolute=312 (≈ 31 ms), set via v4l2-ctl. Lower it (~156) to cut motion blur once the car is moving.
  • Latest-frame-wins capture. A threaded reader keeps only the newest frame (BUFFERSIZE=1) so perception never works on stale frames.
  • The camera is the bottleneck, not the GPU. Depth + YOLO leave the GPU ~50 % idle; a faster camera would be the single biggest perception upgrade.

11 LiDAR

RPLIDAR C1

A Slamtec RPLIDAR C1 — a spinning 360° 2D laser scanner — connects through a Silicon Labs CP2102N USB bridge at 460800 baud (ttyUSB0). It reports model 0x41, firmware 1.01. A custom pure-pyserial driver reads it — no external LiDAR library.

  • On connect, DTR is pulled low so the scanner's motor isn't held in reset.
  • Scan data arrives as 5-byte nodes decoded to (quality, angle, distance): angle = ((b1>>1)|(b2<<7))/64 degrees, distance = (b3|b4<<8)/4 mm. Full revolutions (~10 Hz) are yielded as lists of points; range is trusted to ~12 m.
  • In ROS 2 it publishes /scan (LaserScan, 360 bins) — with a clockwise→counter-clockwise fix to match the ROS convention — feeding SLAM and the obstacle costmaps. A standalone ICP mapper also exists for lifted/hand-carried mapping.
This is what shifted the ports Because the LiDAR's CP2102N enumerated as ttyUSB0, it displaced the steering Nano to ttyUSB1 — the origin of the port-shift trap in §06.

12 GPS + compass

Radiolink SE100

One module carries two sensors on a standard 6-pin Pixhawk connector (VCC, GPS-TX, GPS-RX, SCL, SDA, GND): a u-blox M8N GPS and an IST8310 magnetometer (compass). They wire to the Jetson header two different ways — GPS over UART, compass over I2C (see §05).

GPS

  • NMEA sentences on /dev/ttyTHS1 at 38400 baud — not the u-blox 9600 default.
  • Multi-GNSS; parses GGA/RMC/GSV for fix, satellites, SNR, position.
  • Needs sky view: indoors shows 0 sats / status V (void); outdoors → status A with a lat/lon.

Compass (IST8310)

  • I2C bus 7 at 0x0e; identity check WHO_AM_I(0x00) == 0x10.
  • Read sequence: configure 0x41←0x24 (16× avg) and 0x42←0xC0, trigger a single measurement 0x0A←0x01, poll data-ready 0x02 bit 0, read 6 bytes from 0x03 (X/Y/Z, signed, ≈ 0.3 µT/LSB).
  • Heading = atan2(Y, X), normalized 0–360°.
The compass is the weak link It is currently raw/uncalibrated (needs a 360° spin calibration) and is very sensitive to magnetic fields. Once the motor draws current it will corrupt headings unless the SE100 is mast-mounted well away from the VESC, motor, and power wiring. This is the #1 cause of bad rover compass readings.
Power-off incident (lesson learned) While inserting the compass wires next to the 5 V pins, a momentary 5 V/GND short made the Jetson PMIC cut power to protect itself (worst under MAXN_SUPER's tight current headroom). No damage — but the rule stands: power down before touching the 40-pin header.

13 OLED display

SSD1306 stats screen

A small 128×64 SSD1306 OLED at 0x3c on the same I2C bus as the compass shows live CPU / GPU / memory / temperature at a glance. It runs headless as a systemd service (oled_stats.service), so it comes up on boot with no login. It shares SDA/SCL with the compass without conflict — I2C is addressable, so both devices coexist on the one pin pair the header provides.

16 Gotchas & lessons

Hard-won rules

Resolve serial by identity

Port numbers shift on replug. Always use /dev/serial/by-id/.

VESC needs its battery

No motor battery → no ttyACM0. Check the pack before blaming software.

numpy must stay < 2

numpy 2.x silently breaks the system OpenCV 4.5.4.

Servo gets its own power

A BEC, not the Jetson 5 V. Always common-ground everything.

Keep the compass away from the motor

Phase current corrupts headings — mast-mount it.

One VESC owner at a time

autonav, the web console, and ROS all want ttyACM0. Never two at once.

Power down before touching the header

A live 5 V/GND short trips the PMIC (it did once — no damage).

TensorRT engines are hardware-specific

Rebuild yolo11n.engine if JetPack/TensorRT changes.
